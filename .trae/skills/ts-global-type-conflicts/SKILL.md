# TS global declaration-merge conflicts

When code that calls a standard API stops compiling with an argument type that comes from a completely different world — e.g. `document.body.append(div)` failing with `HTMLDivElement is not assignable to string | Response | ReadableStream` — the cause is almost never the call site. A **global interface has merged with an unwanted declaration**, and TypeScript prefers the foreign member signature over the inherited DOM one.

Typical pollution sources in this repository:

- `worker-configuration.d.ts` generated by `wrangler types` (gitignored, but globs like `"include": ["**/*"]` pick it up). Its HTMLRewriter section declares a global `interface Element` with `append(string | ReadableStream | Response)`.
- `@cloudflare/workers-types` (the whole package is a global script; it replaces fetch/Response/DOM shapes with workerd's).
- Newly added `@types/*` packages or hand-written global `.d.ts` files that re-declare generic names (`Element`, `HTMLElement`, `Document`, `Event`, `Location`).

## Procedure

1. **Recognize the pattern.** The error's expected type is unrelated to the API being called and mentions a non-browser runtime. Multiple files/tests fail at once on the same method. Do not "fix" call sites with casts or by swapping `append` → `appendChild`; that only hides the root cause.

2. **Locate the winning declaration with the probe script.** It resolves a member under the project's own tsconfig and prints the declaration file TypeScript actually uses, plus every declaration file defining a same-named member:

   ```bash
   echo 'document.body.append(document.createElement("div"))' > /tmp/probe.ts
   node .trae/skills/ts-global-type-conflicts/scripts/probe-member.mjs blog-frontend /tmp/probe.ts
   ```

   The first listed file is the merged-in winner (e.g. `worker-configuration.d.ts:1544`). The candidate list confirms which files conflict. Adapt the snippet expression/member to the failing API (e.g. `window.location.assign(x)`).

3. **Confirm how it enters compilation.** Generated files enter through tsconfig globs (`include: ["**/*"]`), triple-slash references, or a dependency's global `.d.ts`. Check whether project code actually needs types from that file; generated runtime-type files are usually replaceable with a minimal shim.

4. **Fix at the source, in order of preference:**
   - **Exclude the generated/global file from the client tsconfig** when the project only needs a small part of it. Keep the exclusion comment factual and name the correct escape hatch (a server-only d.ts with a scoped `/// <reference path="..." />`).
   - **Replace whole-package globals with a minimal local shim** that declares only the used members on uniquely named interfaces (never re-declare `interface Element` globally). This is the established contract in `blog-frontend/src/types/shims.d.ts` for HTMLRewriter.
   - Use separate tsconfigs for server and client when both genuinely need different global shapes.
   - Do not add `as any` / `as unknown as X` at call sites, and do not edit gitignored generated files (they are regenerated).

5. **Verify the full chain:** `npx tsc --noEmit` (0 errors), the project's `npm run typecheck`, its test suite, lint, and a production build. Re-run the probe: the winner must now be `typescript/lib/lib.dom.d.ts` for browser APIs.

## Repository notes

- `blog-frontend/tsconfig.json` excludes `worker-configuration.d.ts` for exactly this reason; `src/types/shims.d.ts` documents why the project must not pull in all of `@cloudflare/workers-types` (it swaps browser fetch/Response/DOM shapes the React components and jsdom tests depend on).
- The worker `src/worker/` project legitimately uses `@cloudflare/workers-types`; never add browser-shape assumptions there, and never export worker-only globals from shared code into the blog client compilation.
- A `.d.ts` that declares global interfaces must use non-colliding names or live inside `declare module`/`declare global { ... }` scopes that do not re-declare DOM interface members.
