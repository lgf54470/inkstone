## 本轮为什么是这四件

四件里三件不是「没有能力」，而是「能力没有出口」：

| 要求 | 已有什么 | 缺什么 |
| --- | --- | --- |
| 离线写入 | 笔记侧 outbox 已跑通（乐观更新、跨标签广播、按序重放） | 那条队列是笔记形状的（`noteId`/`writeId`/`rev` 依赖链），音乐照搬不了；音乐的三处状态直接打 API，断网即 toast + 回滚 |
| 统计面板 | `playCount` 与 `lastPlayedAt` 一直在采集 | 只被用来排序，没有一处读给读者看 |
| 均衡器 | 音频图里已有 3 段（低架 180 Hz / 1 kHz / 高架 4.5 kHz）与响度归一化 | 分辨率而不是链路——缺的是频段表与它的一致性 |
| 订阅公开歌单 | 分享链接已能匿名打开（`ADR-0005`） | 链接是单向的：访客拿到就是终点，没有「再回来」 |

## F6-1 · 断网时的音乐写入（新功能）

**现状**：图书馆三处可写状态（曲目收藏、曲目置顶、歌单旗标）都是「直接打 API，失败即 toast + 回滚」。断网时（`ApiError.isOffline`，status 0）读者的意图直接丢掉，而这恰好是他最想让它留下的时候——地铁里点的那颗心。

**做法**：不把音乐塞进笔记那条队列（形状不同，硬塞会把 `rev` 依赖链拖进音乐域），而是在同一个 IndexedDB 层上开第二条队列，只服务音乐的两类 patch（`trackFlags`、`playlistFlags`）。触发点是两个本来就存在的边界：打开音乐库时的加载路径（`loadLibrary` 先重放再读），以及窗口重新上线（hub 的 `online` 监听，它才是拥有图书馆的那个表面）。

**冲突策略**：一个目标一条待写项，载荷**合并**而不是替换——所以「置顶、取消置顶、再置顶」留在队里的是一条，且此前设过、之后没再动过的字段不会被这次写入抹掉。重放时两种结果要分开：**仍然离线**就停下整队（后面的条目会撞同一张网，队列不丢）；**服务端拒绝**（4xx）是对**取值**的判断，重放还会被拒，于是丢弃该条——丢弃之前先记一次失败（`markMusicWriteFailure`），好让「这条为什么不见了」之后可查。丢弃的条数返回给调用方，由它重新拉一次库来修正乐观状态。

**范围**：`src/client/lib/db/{types,keys,index,store-io,core}.ts`、`music-store/pending-writes.ts`（新）、`music-store/{library-tracks,library-collections,library-load,index}.ts`、`music-hub-modal.tsx`、两语言资源各 1 键。

## F6-2 · 统计面板（新功能）

**为什么只能到「周」这一层**：库里没有逐次播放日志，只有 `playCount` 与 `lastPlayedAt` 两个累计字段。所以面板给的是「本周 / 上周 / 更早」的**直方图**加艺人、标签两个维度的排行，而不是「逐次播放次数」。要按周精确回看收听次数需要新增播放事件表——那是数据模型改动，不在本轮范围（见「已知限制」）。

**做法**：推导逻辑是纯函数（`music-insights.ts`，只吃 `tracks` 与 `tags`，不碰 store），面板只负责画。周起点按本地时区的周一零点算（`weekStart`），空库另有空态文案，避免把「没有数据」画成「全 0 的排行榜」。

## F6-3 · 十段均衡器（refactor，不是新建）

- **频段表落成一个叶子模块**（`music-eq-bands.ts`，自身无 import）：音频图、预设、滑杆标签三处读同一份。这不是洁癖——同一份顺序写在三处会漂成「500 Hz 的滑杆动了 1 kHz 的滤波器」，那听起来像答案错了，而不像控件坏了；而且图不能反向 import store 去问自己有几个频段（`store → player → graph → store` 是环）。
- **首尾是 shelf 而不是 peak**：31 Hz 以下、16 kHz 以上没有相邻频段可以融合，用 shelf 才真的塑形，否则留下一道台阶。
- **旧的三段按覆盖范围迁移**：低架 180 Hz 的值抄到它覆盖的每个频段，1 kHz 同理，4.5 kHz 同理——读者调过的声音不会因为换实现而变平。
- **两个方向都容错**：存储里短于今天的数组按位补齐（表达过的部分保留），越界或非数字按 0 读。

## F6-4 · 公开歌单的回访（新功能）

- **不需要访客标识**：公开端点已经在每首曲目上带 `createdAt`，「上次访问以来新增了什么」是**一次比较**，不是一份订阅记录。因此这条功能不新增任何数据模型、不写服务端、不做鉴权。
- **为什么不复用访客指纹**：分享链路的身份是按 UTC 日加盐轮换的（`ADR-0003`），跨天就认不出同一个人；为了一个便利提示而发明持久标识，正是这个模块一直在避免的追踪。
- **时间戳按 slug 分开存**（`inkstone.playlist-visit.<slug>`）：打开一个歌单不会改写另一个歌单的「看过」。首次访问不报「全部都是新的」——那不是「有什么变化」的答案，是它的缺席。
- **回访提示可关**：提示条上有一个「不再提示更新」，清掉时间戳，当次与之后都不再比较。

### 对比度与 StrictMode：这条功能自己暴露的两处（本轮内修掉）

**F6-5 · 提示条不能把暗文字层级放在强调软底上**（`adf689cf`）。提示条原本整条铺 `--accent-soft`，里面却放了 `--text-tertiary` 与 `--text-secondary`。令牌系统只保证**最高层级**落在强调底色上达标（AGENTS.md「对比度修正」段：最暗层级在强调底色上只有 3.86:1，且无法靠调令牌补救——要让它在 14% 强调底上达标，令牌会深于上一层、层级倒挂）。改成**左侧强调色竖线 + 页面底色**：新增计数的强调色文字、以及「仅记在这台设备上」的暗层级文字，各自落在自己已校准的底色上。行内那枚「新增」徽标保留 `--accent` on `--accent-soft`——那正是按全部 7 个强调色量测过的配对，与侧栏选中行的计数徽标同一种。

**F6-6 · StrictMode 双跑让提示静默消失**（`9cfc4760`）。`main.tsx` 用 `<StrictMode>` 包着，effect 会跑两次；而比对读的「上次访问」时间戳在同一次加载里又被写入，于是第二次读到的是第一次刚写下的值，报出的新增为空——**而读者看到的正是第二次的结果**。症状只在开发模式出现（生产构建不双跑），这正是它容易漏掉的原因：已有的单元测试挂载时没有包 StrictMode，所以 13 例全绿也没发现。修法是把时间戳按 slug 捕获进 ref，**比较只读捕获值、只有写入推进它**，两次跑出同一个答案。

复现是真实的：先写 StrictMode 用例，对旧实现得 **1 failed / 22 passed**（失败的正是这一条），修后 23 例全绿。真实浏览器上的验证见下表。

## 已知限制 / 不做

- **音乐写队列是「后写生效」**：同一目标上更晚的意图覆盖更早的（同字段合并），不做字段级三方合并——队列里保存的是**意图**，不是历史。
- **重放没有退避重试**：只在两个边界触发（打开音乐库、窗口重新上线）；断网期间不做定时探活。
- **统计面板只有两个累计字段**（F6-2）：要真正的「按周收听次数」需要新增播放事件表，属数据模型改动，本轮不做。
- **队列行的常驻收藏/置顶**仍然不做（沿用第五轮 F5-6 的判定：队列语义是顺序，加两枚常驻控件会把 36px 的行挤满，右键与菜单键已到得了）。
- ~~**公开歌单的回访没有端到端门禁**~~ → 已补（`64dfd0ea`），见文末「第七段工作」。补完门禁后又在这条功能上查出四处：比对会把自己刚写下的时间戳读回去（StrictMode 双跑下提示先出后没）、服务端列表缓存 15s 会交回加歌前的副本、`createdAt` 其实是曲目创建时间而不是入单时间、以及头部 logo 上的无效无障碍名。四处都已修：`7954e6bd`（前三条）与 `deaa6ac9`（无障碍名）。
- **均衡器的响度归一化沿用既有实现**（`configureLoudnessNormalization`），本轮只扩频段，没有改归一化算法本身。

## 第七段工作（同日后半段）· 匿名公开歌单页的端到端门禁

用户要求为这条功能补一条门禁，而门禁一旦真正去打开那个页面，就在它身上查出四处（都在单测全绿、两个端到端也绿的状态下活着）：

| # | 症状 | 根因 | 处置 |
| --- | --- | --- | --- |
| F6-8 | 提示先读作「新增 1 首」，随即提示与徽标一起消失 | 回访比对顺手推进了它正在比对的那个时间戳；React 在 StrictMode 下跑两次 effect，第二次读回的正是第一次刚写下的值，而读者看到的正是第二次的结果 | 比对改成纯读；时间戳改由 `useRememberVisit` 在 `pagehide` 写下读者实际看到的最新一条（因此页面打开期间新增的曲目下次仍会被报出，而不是被当成「已看过」） |
| F6-9 | 加歌后重开，列表还是加歌之前的内容 | 服务端列表带 `Cache-Control: public, max-age=15`，而页面用同一个 URL 取数据决定「有没有新东西」 | `transport.request` 新增 `cache` 选项，`publicPlaylist` 用 `no-store` 取（页面每次访问只取一次，代价为零） |
| F6-10 | 把一首**早已在库里**的歌加进歌单，永远报不出「新增」 | 载荷的 `createdAt` 是曲目自己的创建时间，不是它进这个歌单的时间——而「加一首老歌进歌单」正是读者的常见情形 | 歌单详情多取 `pi.created_at` 作为 `addedAt` 下发，比对改用它；新增一例把 `created_at` 改成 1 后入单，断言两个时间戳确实不同 |
| F6-11 | axe 报 `aria-prohibited-attr` | 头部 logo 外层 `span` 挂了 `aria-label`，而 `span` 无有效 role；Logo 自身已是 `aria-hidden` | 去掉该属性（分享笔记页的头部本来就是这么写的） |

**为什么四处都只在真实浏览器里现形**：F6-8 需要 StrictMode 的双次副作用（生产构建不双跑，开发构建才双跑，而单测既不包 `StrictMode` 也不重放 effect）；F6-9 需要真浏览器的 HTTP 缓存；F6-10 需要「加一首老歌」这个只有真实数据才有的形状；F6-11 需要真正跑一遍 axe。四处的共同教训是同一句话：**「只有单测」的页面等于没人看过。**

该门禁现在钉住的是行为而不是存储：首访与无变化的重开都不得报出任何东西；在访客背后加一首曲子后重开，提示必须读作「新增 1 首」、只有那一行带徽标；键盘能 Tab 到「不再提示更新」与曲目行，Enter 播放该行自己的公共流；点过「不再提示更新」后重开必须回到「首次访问」。它不读 `localStorage`，所以实现换一种存法也不会把它变成假绿。
