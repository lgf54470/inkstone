## A. 结论摘要

音乐库仍是本仓库最大的单一业务模块：客户端 **125 个非测试源文件 / 17 908 行** + worker **37 个非测试文件 / 5 931 行** + **120 个客户端测试文件** + 两侧 1 010 行文案。前两轮把「不可用」（413 内容过大、原生确认框）与「不一致」（三个表面的队列能力）都清掉了，本轮的四个点名症状**全部落在同一个类别上：功能都在，但入口语义、默认态与宽容器下的形态没有被真正设计过**。

四个点名的定位结论（详见 §C）：

| 点名 | 结论 | 根因（file:line） | 性质 |
| --- | --- | --- | --- |
| ① 「搜索框后面的清除按钮清不掉搜索内容」 | 成立。按钮画在输入框里、名字叫「清除搜索」，但按下执行的是「清空搜索历史 + 收起浮层」，**输入框里的字一个都不动** | `music-search-box.tsx:274` 把 `onClear` 接到 `popup.clearAll`（`:126` = `clearHistory()` + `close()`） | 一行代码的语义错，且**与右侧「清除历史」按钮同一份实现**——两个不同意图共用一个回调 |
| ② 「左侧沉浸式播放列表默认显示」 | 成立。队列默认折叠，进沉浸层要先点右上角计数才能看到左列 | `music-immersive-queue.tsx:13` `useState(false)` | 默认态选择（宽版该开、窄版该折） |
| ③ 「音乐设置面板 UI 有问题（输入框没对齐、5 个均衡器按钮分两行）」 | 两条都成立，另有第三条同源问题（同一段提示文案在同一屏出现两次） | EQ 预设行 `music-transport-widgets.tsx:347` 恒 `grid-cols-3`（5 个预设 = 3+2）；服务器表单 `music-server-manager.tsx:159/188` 每格自称标签宽度（`flex`），四列互不对齐；提示重复 `music-servers.tsx:15` 与 `music-server-manager.tsx:146` 同为 `music.server_hint` | 组件在两种宽度（224px 弹层 / 整宽设置页）下只有一种形态 |
| ④ 「对比参考项目少了很多功能：音源、设置项、历史搜索」 | 成立，但要分清三类：**音源粒度**（单源开关/单源检索/平台账号）、**设置项**（音量、下载设置、睡眠与倍速的设置页入口、全屏播放器选项）、**搜索历史**（只在 Enter 落库、无逐条删除、在线搜索不入历史） | §E 的逐项对照表 | 产品缺口（跨多轮），不是缺陷 |

对标的总判断（§E-6）：**广度上 inkstone 已经超过参考项目**——本地曲库（拼音全拼与首字母搜索、标签树、sha256 重复检测、元数据补缺、回收站、播放历史、库健康扫描）、引用源体系（R2 / WebDAV / Alist / 直链 / 在线聚合 / 自建 Subsonic・Jellyfin / 播客 RSS）、播放内核（3 段 EQ + 预设、3s crossfade、RMS 响度归一化、A-B 循环、睡眠定时带淡出、视频曲目）、分享页与演示能力都是 otter-music 没有的。**落后的是「把在线音源当第一公民」的那一层**：那边的音源是可开关、可排序、可单源检索、可分别登录的 13 个条目，这边是 1 个聚合开关 + 5 个只能一起查的上游。这不是「做得少」，而是**粒度差一个数量级**——它同时解释了 ④ 里的「音源」与「历史搜索」两问：单源粒度是检索范围的前置条件，而检索范围又是历史记录的意义所在。

## B. 审查方法与取证边界

**做了什么**：把模块当作一个独立 app 逐条走查（侧栏 scope → 工具栏 → 搜索 → 结果三态 → 队列 → 浮窗 → 沉浸层 → 设置页 → 在线源），每条结论都落到 `文件:行`；对参考项目逐目录读它的能力清单（音源表、设置组件、store slice、lib 源实现），只把**有材料支撑**的差异登记为缺口；对既有门禁的断言清单（`scripts/e2e-visual.mjs` 的音乐场景、`scripts/check-contrast.mjs` 的形态）做了逐条核对，判断「哪些新结论能变成断言、哪些只能人工不变量」。

**没有做（边界，如实写）**：沙箱里上游曲库不可达，所以一切「在线行为」的判断依据是**代码契约 + 请求拦截桩 + 单测**，不是真实上游；参考项目只读其源码与 README，**没有运行它**，因此它的能力以「它的材料怎么写」为准（例如「音源自动匹配」我按它的 `AutoMatchSetting.tsx`/`AutoMatchSuffixSetting.tsx` 与 README 记录，未实测）。

## C. 点名四条症状的定位结论

### C-1「点击搜索后不能点击搜索框后面的清除按钮清除搜索内容」

- **定位**：`music-search-box.tsx:274`
  ```tsx
  {text && <SearchClearButton onClear={() => popup.clearAll()} />}
  ```
  而 `popup.clearAll`（`:126-129`）是
  ```tsx
  clearAll: () => { clearHistory(); close() }
  ```
  即：**按钮清的是历史，不是查询**。`text` 仍是原值，`useDebouncedText` 的 `lastSentRef` 也没变，所以输入框连抖动都没有——读者看到的是「按了没反应」。
- **为什么会出现**：这个 popup 有两种形态，`clearAll` 是**历史形态**（空输入 + 聚焦，标题「最近搜索」）里那个「清除历史」动作名（`:293`）。搜索框的 × 直接复用了它，于是两个意图共享一个回调。
- **同源事实**：`music-track-list.tsx:127` 的空态按钮用 `music.search_clear`（「清除搜索」）**语义正确**（它调的是 `setQuery('')`），所以**同一个文案在屏幕上有两种行为**：空态按钮真的清、输入框里的 × 不清。截图 3 的两个红框正是这两处。
- **处置**：FB3-U1（清查询 + 收起浮层；历史另走自己的按钮）。

### C-2「左侧沉浸式播放列表默认显示而不需要点击右上角的按钮才显示」

- **定位**：`music-immersive-queue.tsx:13` `const [queueOpen, setQueueOpen] = useState(false)`。该状态**随表面存活**（不随重开复位，M4/M10 已记录），所以默认折叠意味着：读者每次打开沉浸层，左列下半部分是空的（截图 1 的下半部分），而队列摆在歌词下方那条只有约 3 行的条带里（`music-immersive-player.tsx:235`）。
- **为什么宽版该开**：FB2-U1 已经把队列搬进左列并复用带搜索的 `MusicQueueBrowser`，左列在宽版是 `w-96/w-80/w-72` 的整列，封面 + 元数据 + 传输条通常只占上半（`immersivePaneWidth()`，`music-immersive-player.tsx:63`）。默认折叠等于**把一个已经建好的能力关在门后**。
- **窄版不能照抄**：堆叠（`stacked`）时队列不是一列而是歌词下方的条带（`ImmersiveQueue`，上限 `max-h-40`），默认展开会在 375px 的视口里吃掉约 160px 歌词空间（M10 的实测正是这一形态）。所以「默认显示」的正确形态是**按形态分档**：宽版默认展开，窄版默认折叠，且读者一旦自己折合过就按读者的意思。
- **处置**：FB3-U2。

### C-3「音乐设置面板 UI 有点问题（输入框没有对齐，5 个均衡器按钮分两行）」

三条独立问题：

1. **5 个均衡器预设分两行且第二行缺一格。** `music-transport-widgets.tsx:347` 恒为 `grid grid-cols-3`，`EQ_PRESETS`（`music-eq-presets.ts:16-22`）有 5 个（flat/pop/rock/vocal/bass）→ 宽容器下第一行 3 个各占 ~230px、第二行 2 个，右侧留一格空洞。同一个组件在播放器弹层里是 `w-56`（224px，3 列正合适），在设置页里是**整宽**——这是「一个组件两种宽度只有一种形态」。截图 2 的红框 ② 正是它。
2. **添加服务器的输入框列不对齐。** `music-server-manager.tsx:159` 是 `grid grid-cols-2 gap-2`，而每个格子（`ServerField`，`:188`）是 `<label className='flex items-center gap-2'><span className='shrink-0'>{label}</span>{children}</label>`：**标签宽度由各自文字长度决定**，于是第二列里「服务器类型」（5 字）比「用户名」（3 字）宽，两个输入框的左缘差出一个字——截图 2 里 select 起于 ~1004px、username input 起于 ~957px。第一列同理会随「名称/服务器地址/密码」漂移。
3. **同一段提示在同一屏出现两次。** `MusicServers`（`music-servers.tsx:15`）用 `SectionTitle hint={t('music.server_hint')}` 画一遍「你自己的 Subsonic、Navidrome…」，`AddServerForm`（`music-server-manager.tsx:146`）又画一遍**同一 key**；并且「添加服务器」既是表单小节标题也是提交按钮文案。截图 2 上半屏能直接看到这段说明重复两遍。

其余同屏细节（一并核对，未列为独立项）：EQ 面板在设置页里没有边界（直接铺在分组里，和上下 `SettingRow` 的行节奏不一致）、`Switch` 与滑杆的左右边距与设置页其它行不一致（`MusicEqPanel` 自带 `px-1.5 py-1`）。

- **处置**：FB3-U3（三处一个提交：预设行按容器换挡、表单标签列用 subgrid 对齐、去掉重复说明）。

### C-4「对比参考项目少了很多功能：音源、设置项、历史搜索…」

按三类登记，逐项对照见 §E，这里只给结论：

- **音源（粒度缺失，不是数量缺失）**：`providers/registry.ts` 里只有一条 provider（`gds`），`searchGdsPages`（`providers/gds.ts:39`）**无条件**把 `GDS_SOURCES`（5 个上游）全部查一遍，客户端**没有任何「只查某一个上游」的入口**；设置页里也只有 1 个开关（`music-settings.tsx:84` `ProviderSwitch`）。参考项目在这件事上有：13 个音源条目、逐源开关、**逐源检索范围选择**（截图 6 的「聚合搜索 / 网易云音乐 / Netease / Joox / B站 / 酷我音乐 / Migu / QQ音乐」下拉）、平台账号登录（Netease/QQ/B站，用于曲库与歌单导入）、逐源可用性说明。→ FB3-F1（单源检索范围，本轮做）+ FB3-F2（逐源开关与顺序、平台账号，下一轮，理由见 §H）。
- **设置项**：对照它 `src/components/settings/` 的 28 个组件与截图 4，inkstone 音乐设置页缺：**音量调节**（设置页完全没有；音量只在播放器弹层里）、**下载设置**（音质/目录/是否嵌入封面歌词——inkstone 的「下载」是 Service Worker 离线缓存，无音质与目录选择）、**睡眠定时与倍速的设置页入口**（能力都在，只在弹层与菜单里）、**全屏播放器选项**（参考项目可选 288px/动态，inkstone 的沉浸层尺寸是测量得到的，不是偏好）、以及音乐面的**主题切换**（应用级外观设置里有，与本模块的沉浸背景模式不是同一件事，见 §H 的判断）。→ FB3-F3（音量 + 睡眠/倍速入口，M10）与 FB3-F4（下载设置，M11）。
- **搜索历史**：现状是「只在 Enter 落库」（`library-load.ts:150-156` 的 `commitQuery`）、「只在输入框为空且聚焦时可见」（`music-search-box.tsx:113` `historyMode = !text.trim()`）、「只能整段清空」（`:293`）。三处都能改：线程内的搜索（debounce 触发的在线检索）不落历史、历史不能逐条删、有字时看不到历史（参考项目在有字时把历史与建议并列，见截图 5）。→ FB3-F5（逐条删除 + 记录时机，本轮做）。

## D. 本轮自行发现（点名之外）

### D-1 FB3-U4 ·「没有匹配的歌曲」在在线命中就摆在正上方时读起来像「整站没有结果」

截图 3：上方「在线结果」列出 5 条命中、下方空态写「没有匹配的歌曲 / 『原点』的搜索结果 / 清除搜索」。两句话都对，但同时出现时读者得到的是**互相削弱的信息**：本地 0 命中被读成全网 0 命中（而在线面板恰恰在反驳它）。`music.no_results`（`en-US/music.ts:39`）是整段共用的 key，`NoTracks`（`music-track-list.tsx:120-133`）在 `query.trim()` 时用它当标题、把查询串当描述、把「清除搜索」当动作。
**方案**：查询态空态改为「曲库中没有匹配的歌曲」，并在在线面板可见时补一句指向它（例如「上方是按在线音源搜索的结果」）。**代价**：小（一个 key + 一处条件渲染 + 双语）。**收益**：消除本模块最容易误读的一屏。

### D-2 FB3-U5 · 搜索框右侧的 × 只清查询、不碰历史，但没有任何地方说明历史怎么清

历史形态（空输入 + 聚焦）里才有「清除历史」，而那个形态**要求先删光输入框里的字**。于是读者在「刚搜完一件事」的状态下想清历史，得先把查询清掉（本轮修好之后 × 能用了）、再聚焦、再找那个按钮。**方案**：× 之后把焦点留在输入框（复用现有 `useClickOutside`/`useEscape` 的栈语义），历史形态自然出现；顺带在历史行上提供逐条删除（与 FB3-F5 同一处）。**代价**：小。

### D-3 FB3-P1 · 一次在线检索 = 5 次上游请求 + 5 笔预算，而读者通常只想要一个源

`music-provider-results.tsx:75-82` 的 `useEffect` 在 query 变化 500ms 后调 `searchProviders(query)`；`searchGdsPages` 再用 `Promise.all` 扇出到 `GDS_SOURCES` 的 5 个上游，每个都过 worker 的 `provider` 预算族（`worker/routes/music/budget.ts`，600/小时）。打字停 500ms 就触发一轮，读者连打三次就是 15 次请求。**方案**：单源范围（FB3-F1）落地后，范围选非聚合时只扇出 1 个源；另外**只在查询从未在本次会话搜过时才扇出**（一个按 `(scope, keywords)` 的短 TTL 记忆），把「改一个字再改回来」的成本降到 0。**代价**：中（前者随 FB3-F1，后者是一个纯函数 + 一组单测）。

### D-4 FB3-U6 · 在线结果面板的开关与「单源范围」应该是同一个控件组

面板头部现在是「在线结果」+ 一个 `Switch`（`music-provider-results.tsx:88-90`）。开关只管「聚合源开不开」，而读者真正的第一问是「搜哪儿」。**方案**：把范围选择器放进同一行（参考项目也是这么做的，截图 6），开关留在原位——两个控件、一行、一个语义组。**代价**：随 FB3-F1。

### D-5 FB3-F6 · 设置页的音乐分组顺序与读者的心智顺序不一致

`MusicSettings`（`music-settings.tsx:46-52`）的顺序是「在线音源 → 音乐服务器 → 播放默认」。而读者在设置页里最常改的是播放偏好（音量/EQ/歌词），最少改的是「注册一台自建服务器」。**方案**：顺序改为「播放默认 → 在线音源 → 音乐服务器」，或至少把服务器组折叠。**代价**：小（一次重排 + 断言顺序的用例）。**注意**：这是信息架构判断，不是缺陷，采用与否由维护者定。

### D-6 FB3-C1 · 搜索框的 × 与历史浮层没有浏览器断言

既有门禁里 `music` 的搜索断言覆盖的是「在线结果」「建议浮层的指针与 Escape」，**没有一条断言 × 的行为**——所以 C-1 这种「按了没反应」的缺陷能整轮存在（jsdom 用例只覆盖了 `commitQuery` 与历史 combobox 语义，`music-search-box.test.ts` 全文没有点过 ×）。**方案**：`scripts/e2e-visual.mjs` 的音乐场景补两条（有字时 × 存在 → 按下后输入框为空且库回到全部；历史形态的「清除历史」仍在且只清历史）。**代价**：小，且**先红后改**（先写断言、对 HEAD 跑出红，再实现 FB3-U1）。

### D-7 FB3-C2 · `music.server_hint` 的重复是文案资源缺少「用途分层」的症状

同一条 key 被用在「分组说明」与「表单说明」两个位置（C-3③）。这属于 `i18n:check` 管不到的一类（键一致、双语齐全，但**同一 key 被两种语义消费**）。**方案**：拆成 `music.server_hint`（分组）与 `music.server_form_hint`（表单，写「填完按添加，密码只上行不下行」这类**动作向**说明，而不是复述一遍分组说明）。**代价**：小。

### D-8 FB3-U7 · 沉浸层左列的「时长 · 体积」与队列的计数行都在说「有多少」，但一处可点一处不可点

截图 1 的左列底部是 `05:41 · 0 B`（纯文本），而队列的计数行（`music-immersive-queue.tsx:29`）是可点的开合控件且带 `aria-expanded`。两行视觉同级、行为不同级。**方案**：队列计数行的可点属性有视觉指示（它已有 chevron，属可接受）；本条登记为观察项，随 FB3-U2 一起复核（默认展开后，这一行变成「收起」的入口，读者更容易理解它是控件）。

### D-9 FB3-F7 · 没有「最近播放 / 播放最多」作为在线检索的入口

侧栏有「最近播放」「播放最多」（`scope: recent/plays` 排序），但**在线结果只由关键词驱动**（没有「按最近播放的歌去各源补齐」这类动作）。参考项目也没有，故不是对标缺口；登记为**产品机会**而不是缺陷。**方案**：本地行缺失/失效时，行菜单已有「换源候选」（`openSourceSwitch`），再往前一步是「一键为最近播放里的在线行补齐可用源」。**代价**：大。**建议**：不做，仅登记。

### D-10 FB3-S1 · 新增的单源范围必须落在同一套安全与预算契约里

FB3-F1 会新增一个「范围」参数。它**只能**是 `GDS_UPSTREAM_SOURCES` 的白名单取值（worker 侧 `isProviderSource`，`provider.ts:35-37` 已经从同一常量读取），且**不得**放宽任何出站白名单（`GDS_ALLOWED_HOSTS` 只有一个主机）。范围是**客户端减少请求**的手段，不是服务端信任的输入——本轮实现按此办理，并补一条契约测试（范围取值非法时按未传入处理，绝不拼进 URL）。

### D-11 FB3-C3 · 「默认态」类改动需要一条形态断言，而不只是单测

C-2（队列默认展开）是**几何 + 默认态**，jsdom 断言 store 或 DOM 都不足以验收（AGENTS.md 项目信息里的铁律 4：任何定位/布局能力必须有一条真实浏览器断言）。门禁里 `assertMusicImmersiveQueue` 已经会先归一化再量（`scripts/e2e-visual.mjs:5645-5651`），因此**默认展开后既有断言仍然会绿**——这正是「不会红的断言等于没有」的情形。**方案**：补一条「刚打开沉浸层时，宽版队列就在左列（无需按压）」的断言，并对窄版补「默认折叠」的断言。

### D-12 FB3-U8 · 空态动作按钮的文案与输入框里的 × 同名

`music.search_clear`（「清除搜索」/「Clear search」）同时是 × 的 accessible label 与空态按钮的文字。修好语义后两者**都是清查询**，所以在语义上一致了——但作为可访问名称，「清除搜索」出现在两个控件上时读屏用户会听到两个同名控件。**方案**：× 的 label 保持「清除搜索」，空态按钮改为动作明确的「清除搜索并显示全部」（或「显示全部歌曲」）。**代价**：极小（一个 key）。

### D-13b FB3-C4 · 搜索历史的文案在中英之间不是同一句话

`music.search_history` 中文是「搜索历史」、英文是 `Recent searches`（`en-US/music.ts:120` / `zh-CN/music.ts:120`），而它同时是弹出标题与 `role=listbox` 的可访问名称。`npm run i18n:check` 只校验键齐平，两语的词义漂移它看不见。本轮由浏览器探针实际读到（探针一度按中文的字面匹配而找不到那个列表）。**方案**：统一措辞（建议「最近搜索 / Recent searches」，与片下表「清空历史 / Clear history」的动作语一致），并抽查同类命名。**代价**：极小。

### D-13c FB3-C5 · 整轮视觉门禁在全新实例上必然空读音乐场景

本轮把视觉门禁跑到了底（`INKSTONE_EPHEMERAL_DEV=1` + `scripts/e2e.mjs` 播种，全新实例，接口级 177/177 通过；同一命令下视觉门禁 519 通过 / 5 失败，耗时 370s）后实测：它在「music: the hub lists the seeded tracks」失败并让整个音乐场景 `return`，而它上面的「music: the probe library holds two tracks the browser can open」（读服务端）是绿的——即**夹具确实上传成功，但客户端看不到**。机制：客户端的 `loadLibrary` 带 `LIBRARY_FRESH_MS = 60s` 的「刚刚加载过就信它」窗口（`music-store/library-load.ts:12`），而工具栏稳定性扫描在夹具上传**之前**已经打开过一次库并把空结果记在那里；音乐场景与它相隔不到 60s，于是读数读到那份空缓存。既有各轮之所以绿，是因为跑在积留了探针曲目的长寿命实例（`:7714`）上——换句话：**这条前置条件一直在靠环境的残留数据满足**。**方案**：音乐场景读数前强制一次库刷新（工具栏自带的刷新控件就是读者路径），并在夹具之后就断言「两条探针曲目已进入客户端库」，让失败落在准确的地方。**代价**：小–中（2–4h，已排为 M16）。

### D-13 FB3-U9 · 队列默认展开后，左列在窄高窗口下面临两次滚动

宽版左列 = 封面 + 元数据 + 传输条 + 队列（带搜索）。`IMMERSIVE_WIDE_PANE_WIDTH` 之上左列宽 `w-96`，而沉浸层高度固定 `h-[86vh]`（`music-immersive-player.tsx:118`）。默认展开队列后，**矮窗口**（例如 86vh ≈ 560px）里左列的总需求 = 封面（最大 176px 量级）+ 元数据 + 传输条 + 队列最小高度，可能只够队列显示 2–3 行。既有实现里队列组是 `flex-1 min-h-0 overflow-y-auto`（`music-immersive-queue.tsx:35`），所以**不会溢出、只会挤**——可接受，但需要在 FB3-U2 的门禁里量一次「展开后队列至少显示一行且左列不出现第二个滚动条」。

## H. 已知限制与不做清单

**已知限制（如实记录，不假装覆盖）**：

- 本轮新加的音乐门禁场景（`assertMusicSearchClear` / `assertMusicSettingsLayout` 与重写的 `assertMusicImmersiveQueue`）**尚未在整轮 `e2e-visual.mjs` 里跑到**：该轮在全新的本地实例上于音乐场景的前置读数处 `return`（FB3-C5）。因此 M1/M1b/M2/M3 的几何验收以**同读法的一次性浏览器探针**为据（读数与门禁新增场景完全一致，实测表在 `plan-with-freebuff-3.md`）；探针文件已删除，不留在仓库里当第二套夹具。
- M3 与 M1b 落进了同一个提交（`958f5cdc`）：M1b 的两处文件在先前一次被 i18n 门禁拦下的提交尝试里已进暂存区，随后的路径限定提交把它们一并带上了。不重写已提交历史，登记在计划文档的「入库方式」里。
- 逐项 `npm run test:unit` 全量在 M1 后跑过一次（音乐目录 120 文件 / 955 例），M2/M3 只跑了定向文件与 pre-commit 的 `vitest related`（两者都对改动面全绿）；收尾未再跑一次全量。

- 沙箱内上游不可达：在线检索与导入的一切断言基于**请求拦截桩**与契约测试；「真的能播出声音」没有自动断言（与前两轮同）。
- 参考项目**只读其源码与 README，未运行**：它的能力以材料为准，「车载蓝牙歌词」「分P/合集」这类平台相关能力我没有实测。
- 逐源可用性在 inkstone 是**运行期事实**（失败源提示 + 健康扫描），不是**清单**（没有「某源此刻是否可用」的静态声明）——这是有意的：清单会过期，运行期事实不会。
- 沉浸层队列的折合状态随表面存活（既有设计），因此「默认展开」是**本次打开的默认**，不是每次打开都复位；门禁的读法因此先归一化再量（既有断言如此，本轮新增断言按同一约定写）。
- 窄版（堆叠）默认折叠是**有意的不对称**：条带展开要吃掉约 160px 歌词空间；该不对称在本轮的门禁里被两条断言钉住（宽默认开、窄默认折）。

**全量纳入**：本轮报告的每一项都在 `plan-with-freebuff-3.md` 的表里，逐条做，没有「下一轮」分桶。

**规范红线（这不是「本轮不做」，而是按 `AGENTS.md` 禁止）**：

- **把第三方平台账号 Cookie / 令牌收进本系统**（Netease/QQ/B站 账号登录）：`AGENTS.md` 铁律 1 要求「密钥、令牌、密码、私密凭据不进仓库」「权限最小化」且服务端凭据只走服务端存储；把读者在第三方平台的会话凭据搬运进本系统，等于在别人的授权之上再建一份长期凭据，且无法保证撤销链路。替代路径已经齐备：自建服务器（Subsonic/Jellyfin/Airsonic/Emby）+ WebDAV + Alist + 播客 RSS。**这是规范禁止，不是排期问题**；若将来要做，必须先有 ADR 说明凭据模型与撤销策略，并按铁律走评审。
- **车载蓝牙歌词 / 横屏播放模式**：原生平台能力，Web 端没有对等面（Media Session 已覆盖锁屏与媒体键）；没有可落地的实现路径，登记为环境限制而不是排期项。
